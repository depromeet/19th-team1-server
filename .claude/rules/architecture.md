# 구조 규칙

모든 작업에 적용한다. 구조 설명과 정한 이유는 `docs/architecture.md`에 있다. 이 규칙과 어긋나는 변경이 필요하면 구현하기 전에 사람에게 확인하고, 합의되면 같은 PR에서 이 파일과 문서를 고친다.

## 모듈

| 모듈 | 두는 것 | 코드에서 의존할 수 있는 것 |
| --- | --- | --- |
| `core` | 도메인 모델, 서비스, 경계 인터페이스, 에러 코드, 조회 모델 | 없음. Spring은 `@Service`, `@Transactional`까지 |
| `infra` | 경계 인터페이스의 구현. `storage/mysql`(DB), `external`(LLM·푸시·파일) | `core` |
| `api` | 컨트롤러, 요청·응답 DTO, 예외 변환, 설정, 실행 클래스 | `core` (`infra`·`worker`는 실행 시에만 포함) |
| `worker` | 작업 폴링(`job/`), 예약 작업(`schedule/`) | `core` |

## 위치와 이름

- 각 모듈 안은 기능 단위 패키지로 나눈다(`item/`, `intake/` …). `infra`·`api`·`worker`의 패키지 이름은 `core`의 기능 이름을 따른다.
- 경계 인터페이스는 `core`에, 구현은 `infra`에 둔다. 구현 이름은 기술 이름 + 인터페이스 이름이다. (`ItemRepository` → `JpaItemRepository`)
- JPA 엔티티는 `infra`의 `storage` 패키지에 두고 이름을 `JpaEntity`로 끝낸다.
- 컨트롤러는 `api`의 `web/<기능>/`에 두고 이름을 `Controller`로 끝낸다. 요청·응답 DTO는 `api`에만 둔다.
- `@Scheduled`는 `worker`에만 둔다.
- 에러 코드는 `ErrorCode`를 구현한 기능별 enum으로 `core`의 기능 패키지에 둔다(`ItemError`). 코드 이름은 기능 이름으로 시작한다(`ITEM_NOT_FOUND`).

## 호출

- 진입점(컨트롤러, 워커, 스케줄러)은 `core`의 서비스 클래스를 직접 호출한다. 서비스 인터페이스를 만들지 않는다.
- 진입점에는 로직을 두지 않는다. 로직은 서비스에 둔다.
- 경계 인터페이스는 도메인 모델이나 조회 모델만 주고받는다. JPA 엔티티나 외부 응답 DTO를 내보내지 않는다.
- 기능 간에는 상대 기능의 서비스를 호출하고, 엔티티를 참조하지 않고 ID로 연결한다.

## 도메인 모델

- 항상 지켜야 하는 조건(길이, 형식, 필수 값)은 생성자의 `init` 블록에서 검사한다.
- 새로 만들 때만 적용되는 규칙(초기 상태 등)이 있을 때만 `companion object`에 팩토리 메서드(`create`)를 둔다.
- 모델은 불변으로 둔다. 상태 변경은 모델의 메서드로 하고, 메서드가 바꿀 수 있는 상태인지 검사한 뒤 새 객체를 돌려준다.
- 서비스에서 필드를 읽어 객체를 통째로 다시 만드는 방식으로 상태를 바꾸지 않는다.
- 도메인 모델과 JPA 엔티티의 변환은 `infra`의 변환 함수(`toDomain`, `toEntity`)가 한다. 변환 함수에 규칙을 두지 않는다.
- `sealed interface`는 경우마다 담는 값이 다른 결과 타입에만 쓴다. 상태는 enum으로 둔다.

## 서비스와 조회

- 서비스는 기능당 하나로 시작한다(`ItemService`). 조회용과 변경용으로 미리 나누지 않는다.
- 목록·검색처럼 보여 주기만 하는 조회는 저장소 인터페이스가 조회 모델(`ItemSummary` 등)을 바로 돌려준다. 조회 모델은 `core`에 둔다.
- 규칙 검사나 상태 변경이 있는 흐름은 도메인 모델을 거친다.

## 트랜잭션

- 함께 저장돼야 하는 일은 서비스 메서드에 `@Transactional`을 붙여 한 번에 커밋한다.
- 외부 호출(LLM, 푸시, 링크 수집)을 하는 서비스 메서드에는 `@Transactional`을 붙이지 않는다. "읽기 → 외부 호출 → 저장"으로 끊고, 단계마다 저장소 메서드가 스스로 커밋한다.
