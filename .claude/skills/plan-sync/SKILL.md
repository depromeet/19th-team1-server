# 계획 동기화

`docs/plan/roadmap.md`의 "계획이 바뀔 때"를 수행한다. 수정안을 먼저 만들고, 사람이 승인한 것만 반영한다. GitHub 이슈 수정도 승인한 뒤에만 한다.

## 1. 결정 확인

바뀐 결정을 한 문장으로 되물어 확인한다. 무엇이 포함·제외·이동되는지 모호하면 질문한다.

## 2. 영향 찾기

- `docs/plan/scope.md`에서 결정과 관련된 행을 찾는다. 대상은 기능명세서 항목, 기능명세서 밖의 서버 범위, 범위 밖, 결정 대기 표다. 그 행의 스토리 ID가 영향받는 스토리다.
- `docs/plan/roadmap.md`에서 그 스토리의 행을 찾는다. 그 스토리를 "선행"으로 둔 스토리도 함께 찾는다.
- `ls docs/plan/stories/`로 진행 중인 스토리 파일을 확인한다.
- 이슈 번호가 있는 스토리는 `gh issue view <번호>`로 본문을 읽는다.

## 3. 수정안

아래 순서로 수정안을 만든다. 항목마다 대상(파일 또는 이슈), 지금 문장, 바꿀 문장, 이유를 적는다.

1. `scope.md`: 정해진 결정 대기 행은 지우고, 결과를 해당 표에 반영한다. 문서에는 현재 상태만 적는다.
2. `roadmap.md`: 스토리 행(제목, 주차, 선행, 명세 ID, 담당)과 "밀리면 줄일 것"
3. 진행 중인 스토리 파일의 세부 작업과 참고
4. GitHub 이슈의 제목, 본문(무엇을, 완료 조건, 계획)

진행 중인 스토리가 영향을 받으면, 수정이 반영될 때까지 그 스토리를 멈춰야 한다고 알린다.

## 4. 승인

수정안을 보여 주고 **멈춘다**. 사람은 항목별로 승인하거나 고칠 수 있다.

## 5. 반영

- 승인한 문서 항목만 고친다.
- 이슈는 승인한 항목만 고친다. 본문은 `gh issue view <번호> --json body --jq .body`로 받아 임시 파일에서 고친 뒤 `gh issue edit <번호> --body-file <파일>`로 반영한다. 체크박스 상태는 그대로 둔다. 제목은 `--title`로 고친다.
- 반영한 뒤 `gh issue view`로 바뀐 내용을 확인하고 보고한다.
- 문서 수정은 한 PR에 모은다. 커밋과 PR은 사람이 요청할 때만 한다.

## 흔한 실수

| 실수 | 바로잡기 |
| --- | --- |
| 승인 전에 `gh issue edit`을 실행한다 | 4단계에서 멈춘다 |
| 이슈만 고치고 scope·roadmap은 그대로 둔다 | scope → roadmap → 스토리 → 이슈 순서를 지킨다 |
| 문서에 "~에서 바뀜" 같은 변경 이력을 남긴다 | 현재 상태만 적는다. 이력은 git과 이슈에 남는다 |
| 선행으로 걸린 다른 스토리를 놓친다 | roadmap의 "선행" 열을 거꾸로 따라가 확인한다 |
