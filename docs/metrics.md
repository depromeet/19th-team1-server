# 지표와 이벤트

프리런칭에서 서버가 관리하는 지표와, 지표를 계산하는 데 쓰는 이벤트를 정의한다. 지표는 최소한으로 두고, 쌓인 데이터를 분석해 팀에 기준 수치와 추가 지표를 제안한다. 이벤트를 저장하는 테이블과 기록 코드는 E8-2에서 만든다. 화면 흐름과 명세 ID는 [plan/scope.md](plan/scope.md)에 있다.

## 1. 원칙

- **내용을 넣지 않는다.** 이벤트에 URL, 제목, 요약, 주제어, 메모, 채팅 질문·답변 원문, 카카오 계정 정보를 넣지 않는다. 정해진 값 중 하나인 코드와 숫자만 넣는다.
- **사용자는 내부 `userId`로만 가리킨다.**
- **탈퇴하거나 저장물을 삭제해도 이벤트는 남긴다.** 이벤트는 다른 사용자 데이터처럼 보관한다. 프리런칭 후 처리는 [plan/scope.md](plan/scope.md) 결정 대기 11을 따른다.
- **시각은 UTC로 저장하고, 날짜·주 단위 집계는 KST로 한다.** 주는 월요일에 시작한다.
- **기록 실패가 기능을 막지 않는다.** 이벤트를 기록하지 못해도 사용자 요청은 성공해야 한다.

## 2. 지표

핵심 지표는 1번(방문)이다. 기준 수치(목표값)는 정하지 않고, 데이터가 쌓인 뒤 팀에 제안한다.

| 지표 | 보는 것 | 쓰는 이벤트 |
| --- | --- | --- |
| 1. 방문 (핵심) | 일·주간 방문자 수. 주간 재방문율: 이번 주 방문자 중 지난주에도 방문한 비율 | `user_active` |
| 2. 저장물을 어디서 꺼내 보는지 | 경로별(홈 카드, 채팅, 목록) 저장물 열람 수와 비율, 원본 링크로 이동한 비율. 홈은 카드 클릭률: `home_card_clicked` 수 ÷ `cardCount`가 1 이상인 `home_viewed` 수 | `home_viewed`, `home_card_clicked`, `item_viewed`, `item_original_opened` |
| 3. 채팅으로 활용하는지 | 방문자당 질문 수, 결과 없음 비율(`resultCount` = 0), 결과에서 저장물을 연 비율: `entryPath`가 `CHAT`인 `item_viewed` 수 ÷ `resultCount`가 1 이상인 `chat_question_sent` 수 | `chat_question_sent`, `item_viewed` |

## 3. 이벤트

- **서버**: 서버가 API를 처리하면서 알 수 있는 이벤트다. 서버가 기록한다.
- **화면**: 웹만 알 수 있는 이벤트다. 받는 방법은 5절에서 정한다.

| 이벤트 | 언제 기록 | 속성 (공통 속성 외) | 기록 위치 |
| --- | --- | --- | --- |
| `user_active` | 사용자의 KST 날짜별 첫 인증 요청 | 없음 | 서버 |
| `home_viewed` | 홈 관심사 카드를 조회했을 때 | `cardCount` | 서버 |
| `home_card_clicked` | 관심사 카드를 눌렀을 때 | 없음 | 화면 |
| `item_viewed` | 저장물 상세를 조회했을 때 | `entryPath` | 서버 (`entryPath`는 웹이 상세 조회 요청에 담아 보낸다) |
| `item_original_opened` | 원본 링크로 이동했을 때 | `entryPath` | 화면 |
| `chat_question_sent` | 채팅 질문에 응답했을 때 | `resultCount` | 서버 |

### 공통 속성

| 속성 | 설명 |
| --- | --- |
| `eventName` | 위 표의 이벤트 이름 |
| `userId` | 내부 사용자 ID |
| `occurredAt` | 일어난 시각 (UTC) |

### 속성 값

| 속성 | 값 |
| --- | --- |
| `cardCount` | 보여 준 카드 수 (0~4) |
| `entryPath` | `HOME_CARD`(홈 카드의 관련 저장물), `CHAT`(채팅 결과), `LIST`(저장물 목록), `DETAIL`(상세 화면, `item_original_opened`에만) |
| `resultCount` | 질문에 대해 찾은 저장물 수 |

## 4. 이벤트로 남기지 않는 분석

DB 테이블에 이미 남는 것은 이벤트를 만들지 않고, 필요할 때 SQL로 본다. 저장 수, 자동 정리 성공률과 처리 시간, 메모 입력 여부, 삭제된 저장물(소프트 딜리트라 남는다)이 여기에 해당한다. 이벤트는 DB에 남지 않는 행동(방문, 조회, 클릭, 질문)에만 쓴다.

## 5. 화면 이벤트를 받는 방법

`home_card_clicked`, `item_original_opened`는 웹만 안다. 받는 방법은 **웹팀과 결정**한다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| A. 웹이 서버의 이벤트 수집 API로 보낸다 | 모든 이벤트가 한 저장소에 모여 SQL 하나로 집계한다. `userId`는 서버가 인증 정보로 채워 웹이 식별자를 다루지 않는다. 외부로 나가는 데이터가 없다 | 서버에 API와 저장소가 늘고(E8-2), 웹도 전송 코드를 만든다. 대시보드는 직접 만든다. 페이지를 떠나는 순간의 이벤트(원본 이동)는 웹이 유실되지 않게 보내야 한다 |
| B. 분석 도구(GA4, Amplitude 등)를 쓴다 | SDK만 붙이면 바로 쌓이고, 퍼널·리텐션 화면을 기본으로 준다. 서버 작업이 없다 | 서버 이벤트와 저장소가 갈라져, 합쳐 보려면 내부 `userId`를 외부 도구에 보내야 한다. 외부로 데이터가 나가므로 개인정보 처리방침에 반영이 필요할 수 있다. 도구가 기본으로 모으는 항목(페이지 URL, 제목 등)이 1절 원칙과 부딪혀 꺼야 한다. 광고 차단기로 누락될 수 있다 |

## 6. 남은 결정

| # | 결정 | 정하는 곳 |
| --- | --- | --- |
| 1 | 화면 이벤트를 받는 방법 (5절) | 서버 + 웹 |
| 2 | `entryPath`를 상세 조회에 담는 방식 | 서버 + 웹 |
| 3 | 이벤트 보관 기간 | 팀. [plan/scope.md](plan/scope.md) 결정 대기 11과 함께 |
| 4 | 팀원·테스트 계정을 집계에서 빼는 방법 | E8-2 |
