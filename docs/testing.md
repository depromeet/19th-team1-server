# 테스트 전략

코드 대부분을 에이전트가 쓴다. 테스트는 "에이전트가 쓴 코드가 맞는지"를 사람이 일일이 읽지 않고도 확인하는 수단이다. 그래서 테스트 수보다 **틀린 코드를 통과시키지 않는 것**을 기준으로 방식을 정한다.

## 1. 계층별 방식

| 대상 | 무엇을 확인하나 | Spring | 바깥 의존을 대신하는 것 |
| --- | --- | --- | --- |
| `core` 도메인 모델 | 생성 규칙, 상태 변경, 계산 | 띄우지 않는다 | 없음 |
| `core` 서비스 | 업무 흐름, 예외, 재시도 판정 | 띄우지 않는다. 생성자로 직접 조립한다 | 직접 만든 가짜 구현 |
| `infra` 저장소 | 쿼리 결과, 제약 조건, 동시 실행 | 필요한 만큼 | 실제 MySQL (Testcontainers) |
| `infra` 외부 연동 | 시간 초과·한도 초과·오류 응답을 내부 예외로 바꾸는지 | 띄우지 않는다 | 가짜 HTTP 서버 |
| `api` 컨트롤러 | 요청 검증, 서비스로 넘기는 값, 상태 코드와 응답 형식 | 컨트롤러와 예외 처리기만 | 서비스를 목으로 |
| `worker` | 작업 실행 순서, 실패 처리 | 띄우지 않는다 | 가짜 작업 큐, 가짜 분석기 |
| 전체 | 애플리케이션이 뜨는지, 마이그레이션이 적용되는지, 핵심 흐름 | 전체 | 실제 MySQL |
| 구조 | 모듈·패키지 규칙 | 띄우지 않는다 | — (`ArchitectureTest`) |

전체 컨텍스트를 띄우는 테스트는 느리고 메모리를 많이 쓴다. 핵심 흐름 몇 개만 둔다.

## 2. 가짜 구현, 목, 실제 DB를 쓰는 기준

| 대역 | 쓰는 곳 | 이유 |
| --- | --- | --- |
| 가짜 구현 (경계 인터페이스를 메모리로 구현한 클래스) | 서비스, 워커 테스트 | 실제처럼 동작하므로 "무엇이 저장됐는가"로 검증한다. 구현을 고쳐도 테스트를 고칠 일이 적다 |
| 목 (Mockito) | 컨트롤러 테스트에서 서비스를 대신할 때만 | 컨트롤러가 확인할 것은 값 전달과 변환뿐이다 |
| 실제 MySQL | 저장소 테스트, 전체 테스트 | 쿼리는 실행해 봐야 검증된다 |
| 가짜 HTTP 서버 | 외부 연동 클라이언트 테스트 | 시간 초과와 오류 응답을 실제 통신으로 재현한다 |

**하지 않는 것**

- 서비스 테스트에 목을 쓰지 않는다. "저장소의 이 메서드가 한 번 불렸다"는 검증은 구현을 그대로 옮겨 적은 것이라 틀린 구현도 통과시킨다.
- 쿼리를 목으로 검증하지 않는다. `EntityManager`나 Spring Data 리포지토리를 목으로 만든 저장소 테스트는 쿼리를 한 번도 실행하지 않는다.
- H2 같은 대체 DB를 쓰지 않는다. 작업 획득 쿼리(`SKIP LOCKED`)처럼 MySQL에서만 확인되는 동작이 있다.

**가짜 구현을 만들 때**

- 실제 구현의 계약을 따른다. 번호 발급, 유니크 제약 위반, 없는 대상 조회 시 동작이 실제와 같아야 한다.
- 가짜 구현에 테스트 전용 조회 메서드(저장된 전체 목록 등)를 둬도 된다.
- 시각은 `Clock`을 주입받아 고정한다. 테스트에서 현재 시각을 직접 읽지 않는다.

## 3. 공용 테스트 도구의 위치

Gradle의 test-fixtures(`src/testFixtures`)에 둔다. 다른 모듈의 테스트가 `testImplementation(testFixtures(project(":모듈")))`로 가져다 쓴다.

| 위치 | 두는 것 |
| --- | --- |
| `core/src/testFixtures` | 경계 인터페이스의 가짜 구현, 도메인 객체를 만드는 함수 |
| `infra/src/testFixtures` | 테스트용 MySQL 컨테이너 설정(`MySqlContainerConfiguration`), 저장소 테스트 도우미 |

- 가짜 구현은 테스트 파일마다 새로 만들지 않고 한 곳에 둔다. 인터페이스가 바뀌면 한 곳만 고친다.
- 도메인 객체를 만드는 함수는 기본값을 주고, 테스트는 그 테스트에서 의미 있는 값만 바꾼다.

## 4. 실제 DB를 쓰는 테스트

- 테스트 컨테이너 하나를 여러 테스트가 같이 쓴다. 다른 테스트의 데이터가 남아 있을 수 있다고 전제한다.
- 건수 단언은 전체가 아니라 그 테스트가 만든 사용자·저장물로 좁혀서 센다.
- 커밋 이후의 동작을 확인하는 테스트(작업 획득, 중복 방지)는 테스트 메서드에 `@Transactional`을 붙여 롤백하지 않는다. 실제로 커밋하고, 만든 데이터를 직접 지운다.
- 스키마는 Flyway 마이그레이션이 만든다. 테스트용 스키마를 따로 두지 않는다.

## 5. 작성 규칙

- **같은 PR**: 기능과 테스트를 같은 PR에 넣는다. 버그 수정에는 그 버그를 재현하는 테스트를 추가한다.
- **이름**: 한국어 문장으로 동작을 적는다. (`` `만료된 작업은 다시 획득할 수 있다` ``) 메서드 이름을 옮겨 적지 않는다.
- **구조**: 준비 → 실행 → 확인 순서로 쓰고 빈 줄로 구분한다. 테스트 하나는 동작 하나를 확인한다.
- **단언**: `kotlin.test`와 JUnit의 단언을 쓴다. 단언 라이브러리를 추가하지 않는다.
- **약하게 고치지 않기**: 실패한 테스트를 통과시키려고 단언을 지우거나 느슨하게 바꾸지 않는다. 테스트를 삭제하거나 `@Disabled`로 끄지 않는다. 테스트가 틀렸다면 이유를 PR에 적고 고친다.
- **실행 결과 보고**: 에이전트는 실행한 명령과 결과를 보고한다. 실행하지 못했으면 실행하지 못했다고 적는다.

## 6. 테스트하지 않는 것

| 대상 | 이유 |
| --- | --- |
| 값만 옮기는 코드, 프레임워크가 보장하는 동작 | 깨질 일이 없는 테스트는 유지 비용만 든다 |
| 실제 LLM 호출 | 비용이 들고 팀 공용 키가 필요하다. 자동 테스트에서는 분석기를 가짜 구현으로 대신한다. 응답 품질은 사람이 따로 확인한다 |
| 커버리지 수치 | 기준을 두지 않는다. 수치를 채우려는 테스트가 늘어난다 |

## 7. 실행

```bash
./gradlew build                 # 전체 테스트 + 포맷 검사 (Docker 필요)
./gradlew :core:test            # 모듈 하나
./gradlew :core:test --tests "com.depromeet.team1.core.SomeTest"   # 테스트 클래스 하나
```

PR의 `build` 검사가 전체 테스트를 실행한다. 통과해야 머지할 수 있다.
